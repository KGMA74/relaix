# Protocol

The contract between the control plane and the Android agents.

> **Note on status.** `proto/smsgateway/v1/device.proto` does not exist yet — writing it is
> the first piece of implementation work. This document is therefore the
> **specification that file must match**, not documentation of an existing file. When the
> `.proto` is written, this document is reviewed against it and becomes descriptive.

Rationale for the transport choice (gRPC over WebSocket) is in
[architecture.md](architecture.md#3-why-grpc-and-not-websocket).

---

## 1. Package and versioning

```proto
syntax = "proto3";
package smsgateway.v1;
option go_package = "github.com/KGMA74/relaix-server/gen/smsgateway/v1;smsgatewayv1";
```

File path is `proto/smsgateway/v1/device.proto`; the directory mirrors the package.

**Versioning rule:** within `v1`, only backward-compatible changes — adding a new field with
a fresh number, adding a new `oneof` case, adding an enum value. Never renumber a field,
never change a field's type, never reuse a retired number (mark it `reserved`). A breaking
change means a new package `smsgateway.v2` served alongside `v1`, because the fleet updates
by app store rollout: at any moment phones are running several agent versions and an old
agent must keep working against a new server.

Generated Go and Kotlin code is **committed to the repository**, not generated at build
time, so that neither building the server nor building the app requires `protoc` and a
matching plugin set.

## 2. Service

```proto
service DeviceGateway {
  rpc Enroll (EnrollRequest) returns (EnrollResponse);
  rpc Connect (stream DeviceMessage) returns (stream ServerMessage);
}
```

**`Enroll`** — unary, called once in a device's lifetime. Trades a short-lived enrollment
token for a long-lived device token. Separate from the stream because it has different
authentication; see [architecture.md §7](architecture.md#7-enrollment).

**`Connect`** — bidirectional stream, held open for the device's entire uptime. The agent
opens it at startup and reopens it with backoff whenever it drops. Both directions carry an
envelope with a `oneof` payload rather than being split into several RPCs, for three
reasons: one connection means one keepalive budget on a battery-powered device; one stream
means a single ordering domain, so a job push cannot overtake the registration that
authorizes it; and adding a message type later is a new `oneof` case rather than a new RPC
that old servers do not implement.

## 3. Cross-cutting decisions

### `device_token` on every message

Every `DeviceMessage` carries `device_token`, rather than sending it once in a handshake at
stream open.

The handshake approach binds authority to the *connection*: after the first frame, the
server trusts everything arriving on that stream because of something that happened
earlier. Per-message tokens make every frame independently verifiable — the server
authenticates and authorizes each message on its own terms, holds no per-connection auth
state, and a frame injected into an established stream is rejected on its own merits rather
than inheriting trust from the handshake. It also means the gRPC handler stays a pure
function of the message, which matters for the V2 cross-instance forwarding: a message
forwarded to a peer instance carries its own proof and needs no session context to travel
with it.

The cost is a few dozen bytes per message. On a link that is already carrying SMS bodies
and TLS overhead, that is not the constraint.

The token is an opaque server-issued string. The server compares against a stored hash, not
plaintext.

### `signal_strength` as a normalized 0–4 level

Not raw dBm, not ASU.

Android reports signal on a different raw scale per radio technology — GSM RSSI, LTE RSRP,
and NR SS-RSRP occupy different numeric ranges, and −100 means quite different things
across them. A server comparing raw values across a mixed fleet would be comparing
incomparable numbers. The platform already exposes a vendor-calibrated bucketing
(`SignalStrength.getLevel()`), so the agent reports that bucket:

| Level | Meaning |
| --- | --- |
| 0 | no signal / unusable |
| 1 | poor |
| 2 | moderate |
| 3 | good |
| 4 | great |

That is exactly the granularity the scheduler needs — it is deciding whether a phone is fit
to receive work, not drawing a coverage map. If a real diagnostic use case appears later, a
separate raw field can be added without touching this one.

### Client-generated IDs and idempotency

Job IDs are assigned by the server when the job is created and echoed in every message
about that job; `message_id` on each envelope is generated by the sender. Both exist so that
retries are safe: job delivery to a device and result delivery back are both at-least-once
(see [architecture.md §5](architecture.md#5-the-scheduler)), so **the agent must not send an
SMS twice for a job ID it has already handled**, and the server must tolerate receiving the
same `JobResult` more than once.

### Timestamps

All timestamps are `google.protobuf.Timestamp`, UTC. No local time crosses the wire — the
phones are portable and their time zones are not the server's business.

## 4. Enrollment messages

### `EnrollRequest`

Sent once, unauthenticated except for the enrollment token itself.

| Field | Type | Purpose |
| --- | --- | --- |
| `enrollment_token` | `string` | The single-use token scanned from the QR code. Consumed atomically by the server; a second use fails. |
| `device_info` | `DeviceInfo` | Who is enrolling — model, OS version, phone number, and so on. Recorded on the new device row. |

### `EnrollResponse`

| Field | Type | Purpose |
| --- | --- | --- |
| `device_id` | `string` | Server-assigned stable identifier. This is the value callers pass as `deviceId` on `POST /send`, and it survives reinstalls of nothing — a re-enrolled phone gets a new one. |
| `device_token` | `string` | Long-lived credential. The agent stores it and puts it on every subsequent message. Returned exactly once; the server keeps only a hash. |

### `DeviceInfo`

Descriptive, sent at enrollment and again at registration so the server can refresh it after
an OS update or a SIM swap.

| Field | Type | Purpose |
| --- | --- | --- |
| `label` | `string` | Human-readable name for the operator's benefit ("desk phone", "SIM Orange 2"). Shown in `GET /devices`. |
| `phone_number` | `string` | The device's own MSISDN, E.164. This is the number recipients will see, since there is no custom sender ID. May be empty — Android cannot always read it from the SIM. |
| `manufacturer` | `string` | e.g. `Samsung`. Diagnostics. |
| `model` | `string` | e.g. `SM-A536B`. Diagnostics. |
| `os_version` | `string` | Android release, e.g. `14`. Diagnostics, and a hint for platform-specific SMS quirks. |
| `agent_version` | `string` | Agent app version. Needed to interpret behaviour during a staged rollout and to spot phones that never updated. |
| `carrier` | `string` | Network operator name as reported by the SIM. Relevant because sending limits are per carrier. |
| `sims` | `repeated SimInfo` | Every SIM the handset can send from. Empty on a phone that cannot enumerate them. |
| `hardware_id` | `string` | Stable identifier of the handset (`ANDROID_ID`: scoped to the app's signing key, the user and the device — it survives a reinstall, not a factory reset). Read on `Enroll`: a phone that enrolls again takes back its existing device, id and history included, instead of adding a second one. The server stores only an HMAC of it, keyed by `RELAIX_HARDWARE_ID_KEY`. Empty from older agents, which enroll as a new device every time. |
| `time_zone` | `string` | IANA zone the phone is set to. The default zone for its availability windows (§9), so "08:00" means eight o'clock where the phone is. |

### `SimInfo`

A dual-SIM handset is really two sending nodes: the carrier meters each SIM
separately, and the number a recipient sees belongs to the SIM rather than the
phone. `phone_number` and `carrier` above describe only the *default* SMS
subscription — what a single-SIM phone has, and what a dual-SIM phone would
send from if nobody said otherwise.

| Field | Type | Purpose |
| --- | --- | --- |
| `subscription_id` | `int32` | Android's subscription id, and the value `SendSmsJob.subscription_id` refers to. Deliberately not the slot: slots are reused when a SIM is swapped, which would silently redirect traffic to a different number. |
| `slot_index` | `int32` | Physical slot, 0-based. For the operator's benefit — "the one in the top tray" is how people talk about SIMs — never for routing. |
| `phone_number` | `string` | MSISDN in E.164 when the platform will say. Often empty. |
| `carrier` | `string` | Network operator for this SIM. |
| `display_name` | `string` | What the user named it in Android settings. |
| `is_default_sms` | `bool` | Whether this is the subscription used when a job names none. |

## 5. Stream envelopes

### `DeviceMessage` — device → server

```proto
message DeviceMessage {
  string message_id = 1;
  string device_token = 2;
  google.protobuf.Timestamp sent_at = 3;
  oneof payload {
    Register  register  = 10;
    Heartbeat heartbeat = 11;
    JobAck    job_ack   = 12;
    JobResult job_result = 13;
    Leave     leave     = 14;
    PolicyUpdate policy_update = 15;
  }
}
```

| Field | Type | Purpose |
| --- | --- | --- |
| `message_id` | `string` | Sender-generated unique id (UUID). Lets the server deduplicate a message replayed after a reconnect, and ties log lines on both sides together. |
| `device_token` | `string` | Authenticates this message. Present on every message — see §3. |
| `sent_at` | `Timestamp` | When the agent produced the message. Compared against server time to detect a phone with badly skewed clock, and to measure queueing delay separately from network delay. |
| `payload` | `oneof` | Exactly one of the message bodies below. A `oneof` rather than four optional fields so that "exactly one" is enforced by the schema instead of by a validation function. |

### `ServerMessage` — server → device

```proto
message ServerMessage {
  string message_id = 1;
  google.protobuf.Timestamp sent_at = 2;
  oneof payload {
    RegisterAck register_ack = 10;
    SendSmsJob  send_sms_job = 11;
    CancelJob   cancel_job   = 12;
    Ping        ping         = 13;
    DevicePolicy policy      = 14;
  }
}
```

No token in this direction: the device authenticated the server by TLS when it dialed, and
the stream it is reading is one it opened itself.

## 6. Device → server payloads

### `Register`

First message on every new stream. Announces that this device is now reachable on this
connection; the server responds with `RegisterAck` and adds it to the hub.

| Field | Type | Purpose |
| --- | --- | --- |
| `device_info` | `DeviceInfo` | Refreshed on every connect, so the server's view tracks OS updates, app updates, and SIM changes without a separate flow. |
| `health` | `DeviceHealth` | Initial health snapshot, so the scheduler can consider the device immediately rather than waiting for the first heartbeat. |
| `pending_job_ids` | `repeated string` | Jobs the agent believes it still holds from a previous connection. Lets the server reconcile after a reconnect instead of blindly re-dispatching work that is already in flight on the handset. |

### `Heartbeat`

Sent on a fixed interval. Two jobs: prove liveness, and carry fresh health.

| Field | Type | Purpose |
| --- | --- | --- |
| `health` | `DeviceHealth` | Current snapshot. The scheduler reads this to decide readiness. |

A device whose heartbeats stop is marked stale by the hub after a timeout and removed from
the ready set, even if the TCP connection has not yet failed — a phone that has driven into
a tunnel often leaves a socket that looks fine for minutes.

### `DeviceHealth`

| Field | Type | Purpose |
| --- | --- | --- |
| `battery_level` | `int32` | 0–100. A phone below a threshold is deprioritized; sending SMS on a dying battery risks the agent being killed mid-job. |
| `is_charging` | `bool` | A charging phone at 15% is fine; an unplugged one at 15% is not. The pair is more informative than the level alone. |
| `signal_strength` | `int32` | Normalized 0–4 — see §3. Level 0 means the device cannot send and must be excluded from the ready set. |
| `network_type` | `string` | e.g. `LTE`, `NR`, `GSM`. Diagnostic context for the signal level. |
| `sim_ready` | `bool` | Whether the SIM is present and unlocked. A phone can be perfectly healthy and still have no usable SIM. |
| `sent_last_hour` | `int32` | Count of SMS sent in the trailing hour, as counted by the agent. Feeds per-device rate limiting so the fleet does not trip a carrier's anti-spam thresholds. Advisory in V1; the server-side enforcement is a backlog item. |
| `permissions_ok` | `bool` | Whether `SEND_SMS` and the other required runtime permissions are currently granted. A user can revoke them at any time, and the failure mode is otherwise a device that accepts jobs and fails every one. |
| `sims` | `repeated SimHealth` | Per-SIM signal, readiness and hourly count. Empty on a single-SIM phone, where the fields above already say it. |

### `SimHealth`

`SimInfo` carries a SIM's identity, which changes only on a swap; this carries
what a heartbeat refreshes. Keyed by `subscription_id`.

`sent_last_hour` is the field that matters most here: the per-device total is
the sum across SIMs, and rate limiting on it is wrong, because two SIMs each
sitting at their carrier's ceiling look identical to one device at twice the
limit.

### `JobAck`

Sent as soon as the agent receives a job, before attempting to send.

| Field | Type | Purpose |
| --- | --- | --- |
| `job_id` | `string` | Which job. |
| `accepted` | `bool` | Whether the agent will attempt it. False when the device knows it cannot — no SIM, permissions revoked, rate cap reached. |
| `reason` | `string` | Why it was refused; empty when accepted. Surfaced in `job_events`. |

The ack matters because "the server wrote the job to the stream" is not evidence the phone
got it. A fast, explicit refusal also lets the scheduler reassign the job to another device
on the next tick instead of waiting for a timeout.

### `JobResult`

Terminal outcome, sent once the platform reports back.

| Field | Type | Purpose |
| --- | --- | --- |
| `job_id` | `string` | Which job. |
| `status` | `JobStatus` | Outcome — see enum below. |
| `error_code` | `string` | Platform or carrier error identifier when failed, e.g. the `SmsManager` result code. Stable enough to match on in automation. |
| `error_message` | `string` | Human-readable detail for operators. |
| `parts_sent` | `int32` | Number of SMS parts actually sent. A long or non-GSM-7 body is split into several billed messages; the caller needs this to reconcile cost. |
| `completed_at` | `Timestamp` | When the platform reported the outcome on the device. |

`JobResult` may arrive more than once for a job after a reconnect; the server treats a
repeat for an already-terminal job as a no-op.

### `JobStatus`

```proto
enum JobStatus {
  JOB_STATUS_UNSPECIFIED = 0;
  JOB_STATUS_SENT        = 1;
  JOB_STATUS_DELIVERED   = 2;
  JOB_STATUS_FAILED      = 3;
  JOB_STATUS_CANCELLED   = 4;
}
```

`SENT` and `DELIVERED` are distinct on purpose: `SENT` means the handset handed the message
to the network, `DELIVERED` means a delivery report came back from the recipient's network.
Many carriers never return delivery reports, so `DELIVERED` must be treated as a bonus, not
as the expected terminal state — a caller that waits for it will wait forever on some
networks. The zero value is `UNSPECIFIED` per proto3 convention, so an unset field is never
mistaken for a real status.

### `Leave`

The operator forgot the enrollment on the phone. Sent while the token still exists, so the
server can retire the device — exactly as `DELETE /devices/{id}` would: jobs keep their
history, the token stops authenticating — and close the stream. Best-effort by nature: a
phone offline at that moment cannot say goodbye and stays listed until an operator removes
it.

| Field | Type | Purpose |
| --- | --- | --- |
| `reason` | `string` | Free text for the server log. |

### `PolicyUpdate`

The operator edited this phone's rules on the phone itself. The server normalises and
validates them, stores them under the next version, and answers with the stored
`DevicePolicy` (§7) — the phone's confirmation and its new copy. Rules that do not validate
are not stored; the phone is sent the current ones instead, so its copy never drifts from
what the scheduler enforces. Last write wins between the phone and the dashboard.

| Field | Type | Purpose |
| --- | --- | --- |
| `policy` | `DevicePolicy` | The whole rule set; `version` and `updated_at` are ignored, the server assigns both. |

## 7. Server → device payloads

### `RegisterAck`

| Field | Type | Purpose |
| --- | --- | --- |
| `accepted` | `bool` | False when the token is invalid or the device has been disabled by an operator. |
| `reason` | `string` | Why, when refused. The agent shows this rather than retrying blindly. |
| `heartbeat_interval_seconds` | `int32` | How often to heartbeat. Server-controlled so the cadence can be tuned fleet-wide without shipping a new app — the trade-off between detection latency and battery is an operator's call. |
| `stale_job_ids` | `repeated string` | Of the `pending_job_ids` the device reported, those the server considers dead. The agent drops them instead of sending a message the server already gave up on and possibly re-sent elsewhere. |
| `policy` | `DevicePolicy` | The device's current rules (§9), so a phone that reconnects shows what the server enforces, whatever changed while it was away. |

### `SendSmsJob`

The actual work.

| Field | Type | Purpose |
| --- | --- | --- |
| `job_id` | `string` | Server-assigned. The idempotency key: an agent that has already handled this id must not send again. |
| `recipient` | `string` | Destination number, E.164. |
| `body` | `string` | Message text, UTF-8. The agent, not the server, splits it into parts — part counting depends on encoding decisions the platform makes. |
| `priority` | `int32` | Carried through for the agent's local ordering when it holds several jobs at once. Scheduling priority is applied server-side; this is only about the order of an already-assigned batch. |
| `expires_at` | `Timestamp` | After this, the agent must not send and should report the job failed. Prevents a phone that was offline for hours from delivering a stale OTP on reconnect — late delivery of a time-sensitive message is worse than none. |
| `subscription_id` | `int32` | Which SIM to send from, matching a `SimInfo.subscription_id` the device reported. Zero means the handset's default SMS subscription, which is what every job carried before this field existed. A subscription the device does not have is refused in `JobAck` rather than quietly sent from another SIM: the recipient sees the sender's number, so substituting one would bill the wrong SIM and break any reply the caller expected. |

### `CancelJob`

| Field | Type | Purpose |
| --- | --- | --- |
| `job_id` | `string` | Job to abandon. |

Sent when `DELETE /jobs/:id` arrives for a job already pushed to a device. Best-effort: once
the handset has passed the message to the network there is no recall, so the agent cancels
only if it has not sent yet, and reports the real outcome either way.

### `DevicePolicy` (as a `ServerMessage` payload)

Sent when the rules change — from the dashboard, or as the answer to a `PolicyUpdate`.
Replaces the phone's copy. See §9 for the message itself.

### `Ping`

Empty. Application-level liveness check on top of HTTP/2 keepalive, used to detect a
half-open connection that the transport still believes is healthy. The agent responds with
its next heartbeat.

## 8. Connection lifecycle

```
agent                                                          server
  │                                                              │
  │  Enroll(enrollment_token, device_info)         [unary, once] │
  ├─────────────────────────────────────────────────────────────►│
  │  EnrollResponse(device_id, device_token)                     │
  │◄─────────────────────────────────────────────────────────────┤
  │                                                              │
  │  Connect()                                    [stream opens] │
  ├═════════════════════════════════════════════════════════════►│
  │  Register(device_info, health, pending_job_ids)              │
  ├─────────────────────────────────────────────────────────────►│
  │  RegisterAck(accepted, heartbeat_interval, stale_job_ids)    │  hub: register
  │◄─────────────────────────────────────────────────────────────┤
  │                                                              │
  │  Heartbeat(health)                             [every N sec] │  hub: heartbeat
  ├─────────────────────────────────────────────────────────────►│
  │                                                              │
  │                                    SendSmsJob(job_id, ...)   │  scheduler → hub
  │◄─────────────────────────────────────────────────────────────┤
  │  JobAck(job_id, accepted)                                    │
  ├─────────────────────────────────────────────────────────────►│
  │  ... SmsManager sends ...                                    │
  │  JobResult(job_id, SENT, parts_sent)                         │  → callback watcher
  ├─────────────────────────────────────────────────────────────►│
  │  JobResult(job_id, DELIVERED)              [if carrier says] │
  ├─────────────────────────────────────────────────────────────►│
  │                                                              │
  │  ✗ connection lost                                           │  hub: unregister
  │  reconnect with exponential backoff, Register again          │
```

On reconnect the agent always re-registers and reports `pending_job_ids`; the server
reconciles rather than assuming either side's view is authoritative.

## 9. Device rules

`DevicePolicy` says when a device takes work and for which recipients. The server holds it
and is the only one that enforces it: the scheduler hands a job to a device — and picks the
SIM — only where the rules allow it now. The dashboard and the phone both edit it, as views
of the server's copy. Every field's empty value means "no restriction", so the zero policy
is a phone that sends anything, any time.

Two kinds of refusal, treated differently. **Not now** — outside the hours, or at a send cap
— is waited out: a queued job stays pending, an `immediate` one fails. **Never** — no rule
accepts the recipient — fails at once (`no_device_accepts` when no enabled device would ever
take it, `rejected_by_device_rules` when a device named by `deviceId` refuses it), because
waiting cannot change that answer.

| Message | Field | Purpose |
| --- | --- | --- |
| `DevicePolicy` | `version` | Server-assigned, +1 on every change. Tells a holder whether its copy is current. |
| | `availability` | When the device takes work. |
| | `accept` | Which recipients it takes. |
| | `sims` | Per-SIM rules, on top of the device's: a SIM must satisfy both. |
| | `limits` | Caps for the device, all SIMs together. |
| | `updated_at` | When it last changed. |
| `Availability` | `time_zone` | IANA zone the windows are read in. Empty: the phone's `DeviceInfo.time_zone`, then UTC. |
| | `windows` | Available while inside any. None: always available. |
| `TimeWindow` | `days` | ISO weekdays, 1 = Monday … 7 = Sunday. Empty: every day. |
| | `start_minute`, `end_minute` | Minutes since midnight, end exclusive. An end at or before the start runs past midnight: 22:00–06:00 is one window. Both 0 is the whole day. |
| `AcceptRules` | `countries` | ISO 3166-1 alpha-2, matched on the recipient's calling code — narrowed by area code where countries share one (+1 268 is Antigua). The US and Canada cannot be told apart: allowing one allows both. Empty: any country. |
| | `recipient_pattern` | RE2 expression the E.164 recipient must match (unanchored). Empty: any number. |
| `SendLimits` | `per_hour`, `per_day` | Caps over sliding windows (60 minutes, 24 hours), counted by the server in messages handed to the device — a multipart message counts once — including those still in flight. 0: no cap. A device or SIM at its cap is "not now". |
| `SimPolicy` | `subscription_id` | Which SIM, as in `SimInfo`. |
| | `disabled` | Never send from this SIM. |
| | `accept`, `availability`, `limits` | As above, for this SIM alone, narrowing the device's. |

When several SIMs may take a job, the default SMS SIM is tried first. The SIM the scheduler
settles on travels in `SendSmsJob.subscription_id` and is recorded on the job, which is also
what per-SIM caps count.

## 10. USSD and received SMS

Two additions beside sending SMS, both opt-in per agent.

**Capabilities.** `DeviceInfo.capabilities` lists what an agent can do beyond SMS. An older
agent drops a `ServerMessage` payload it does not know without a word, so the server never
pushes one to an agent that has not announced it: a job it cannot run fails at once with
`unsupported_by_device` instead of sitting assigned to a phone that never saw it.

| Capability | Meaning |
| --- | --- |
| `ussd` | Runs a `UssdJob` without `replies`: one request, one answer. |
| `ussd_menu` | Also answers the menus a code opens (`replies`). |
| `inbound_sms` | Forwards received SMS as `SmsReceived`, under `DevicePolicy.inbound`. |

### `UssdJob`

A USSD job is a job like any other — acknowledged with `JobAck`, finished with `JobResult`,
retried, cancelled, called back — sent to the one device the caller named: a code runs
against one SIM's account, so another phone's answer would be about another account. Device
rules apply only through their availability hours; recipient rules and send caps concern SMS.

| Field | Purpose |
| --- | --- |
| `job_id` | The idempotency key. A code can move money: an agent that has seen it never runs it again, not even after an interrupted first run. |
| `code` | What is dialed, e.g. `*144#` or `*144*2*1*70000000*5000#`. |
| `subscription_id` | The SIM to dial from; 0 is the default. A SIM the device does not have is refused (`JobAck.permanent`). |
| `expires_at` | After this the agent does not dial and reports the job failed. |
| `replies` | Typed in order into the menus the code opens. Empty: the code alone. Only sent to a `ussd_menu` agent. |

The outcome is a `JobResult`: `SENT` when the network answered, with each screen it displayed
in `responses`; `FAILED` otherwise, with what was displayed before it stopped. Android's
`sendUssdRequest` runs one request at a time per handset, so an agent runs USSD jobs one
after the other.

A job created with `sensitive` (the code or a reply carries a PIN) never shows its code or
replies through the API, and the server wipes both once the job is over. Agents do not write
the code to disk.

### `SmsReceived` and `SmsReceivedAck`

`DevicePolicy.inbound` (`InboundRules`) says which received SMS a phone forwards: none unless
`enabled`; then those from `senders`, matched whole and ignoring case, or every sender when
the list is empty. The phone applies the rules before anything leaves it, and the server
applies them again on arrival.

| Message | Field | Purpose |
| --- | --- | --- |
| `SmsReceived` | `id` | Agent-generated, stable across resends: the server records one message per device and id. |
| | `sender` | Alphanumeric sender id or number, as the network presented it. |
| | `body` | The whole text, multipart messages joined. |
| | `received_at` | When the network delivered it. |
| | `subscription_id` | The SIM it arrived on; 0 when unknown. |
| `SmsReceivedAck` | `ids` | The server is done with these: the agent may forget them. |

The agent keeps a received message on disk until it is acknowledged, and sends it again on
every reconnect, so a message received offline still arrives. The server acknowledges what it
recorded and also what it refused (not covered by the rules, malformed) — resending those
would meet the same answer — but not what it failed to record, which the phone sends again.
Recorded messages are listed by `GET /inbox` and posted, signed like job callbacks, to the
account's inbound webhook (`RELAIX_INBOUND_WEBHOOK_URL`).

## 11. Automations and the PIN vault

An automation is a small rule the phone runs by itself on each received SMS — offline
included — then reports. It belongs to the device's rules (`DevicePolicy.automations`), so
it is edited in the dashboard, versioned and pushed like the rest of them; an agent lists
`automations` (and `automation_reply_sms`, `automation_webhook`, `automation_ussd`) in its
capabilities.

| Message | Field | Purpose |
| --- | --- | --- |
| `Automation` | `id`, `name`, `enabled` | `id` is assigned by the gateway when empty. |
| | `subscription_id` | The SIM it listens on; 0: any. |
| | `senders` | Matched whole, ignoring case. Empty: any sender. |
| | `pattern` | Must be found in the body. Its named groups — `(?<amount>[0-9 ]+)`, names a letter then letters or digits — are the fields. The syntax both RE2 and Java accept; the gateway compiles it with RE2. |
| | `conditions` | `field op value`, all must hold. `eq` `ne` `contains` compare text ignoring case; `gt` `gte` `lt` `lte` compare numbers, spaces dropped and a comma read as a decimal point (`"5 000"`, `"10,25"`). |
| | `actions` | Run in order; the first failure stops the run. |
| | `limits` | Runs per sliding hour and day, counted on the phone. |
| `ForwardAction` | | The SMS goes to the gateway as `SmsReceived` with `automation_id` and `fields`; the gateway checks it against the automation as stored, and lists and posts it like any received SMS. |
| `ReplySmsAction` | `to`, `text` | An SMS from the SIM it arrived on. `to` must render to an E.164 number — never an alphanumeric sender, never the phone's own number. |
| `WebhookAction` | `url`, `body`, `secret` | POSTed by the phone itself, kept until the receiver answers 2xx (or 4xx), signed with `secret` like the gateway's callbacks. Empty `body`: a JSON object with the automation, the SMS and its fields. |
| `UssdAction` | `code` | A USSD template; may contain `{pin}`. |

Templates replace `{name}` with a field or one of `{sender}` `{body}` `{receivedAt}` `{sim}`.
The gateway refuses a template naming a field the automation does not have. The cases in
`server/policy/testdata/automation_vectors.json` are run by the gateway, the agent and the
dashboard's tester alike.

A run is recorded on the phone before its first action — one per automation and SMS, so a
crash never runs it twice — and reported as `AutomationRun` once over, kept until the
gateway acknowledges it (`AutomationRunAck`). A USSD step reports its code with `{pin}`
unresolved.

**The PIN vault.** A SIM's PIN is set on the phone, behind the screen lock, encrypted with a
key from the Android keystore, and never leaves it. `{pin}` in a code — an automation's
`UssdAction`, or a `UssdJob` sent to an agent listing `ussd_pin` — is replaced on the phone,
and only when the code matches a template its owner **approved on the phone** for that SIM,
within the caps set there: the largest `{amount}` per operation, operations and total per 24
hours. The gateway can ask for a code; it cannot widen what may use the PIN. A template
changed from the dashboard is a new string, and needs approving again. A refusal fails the
job with `PIN_REFUSED`, or the run's step.
